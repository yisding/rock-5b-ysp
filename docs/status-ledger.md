Upstream has known since **2022-08-31**, when Yunfei Wang reported the mirror-image half (`begin_cpu_access` → `iommu_dma_sync_sg_for_cpu` → `arch_sync_dma_for_cpu(sg_phys(sg))`, versus our `end_cpu_access`/`for_device`); Christian König replied that `system_heap_dma_buf_begin_cpu_access()` "is exactly doing what this patch tries to prevent" and that the dma_heap "is doing something which it shouldn't be doing", and in a 2024 thread that "you should never touch the pages in the sg_table in the first place… the long term plan is actually to completely remove the pages from that interface… there is no solution for that." The stalemate is structural, not neglect: the `begin_cpu_access` kerneldoc mandates the *outcome* ("ensure that the memory is actually coherent for cpu access") while saying nothing about mechanism, and no portable API exists for cache maintenance without a `struct device` — the only devices in reach being the attached importers'. A sharp corollary measured here: `dma_direct_sync_sg_for_cpu()` derives the address from `dma_to_phys(sg_dma_address(sg))` and never reads `page_link`, while `iommu_dma_sync_sg_for_cpu()` must use `sg_phys()` because an IOVA cannot be cheaply inverted — so identical dma-heap code is correct on a direct-DMA system and fatal on an IOMMU one, and the heap never calls `sg_page()` itself. Without the option the violation is harmless (reading `page_link` for pages you allocated works), which is why every ARM SoC shipping dma-heaps behind a non-coherent VPU carries it latently and none crash. Fix options were re-evaluated against the source and two of the four earlier sketches are blocked: a core-side bracket needs an ABI addition because `struct dma_buf_attachment` has **no `sgt` field** (the core keeps no reference to the tables it mangles, which live in exporter-private `attach->priv`) plus a locking answer since `dma_buf_begin_cpu_access()` only `might_lock()`s resv; and syncing from the pristine `buffer->sg_table` silently skips the swiotlb bounce sync because the origin carries no DMA flags. `cma_heap.c` shares the identical shape, so any fix covers both, and those are the only two of 25 in-tree `.map_dma_buf` exporters affected.
