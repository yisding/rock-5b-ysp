## Short answer

RK3588 has AV1 decode hardware, and the forward-port kernel exposes it through
RKMPP. The RKMPP AV1 backend is part of the single forward-port line rather than
a separate variant:

- The forward-port exposes RKVDEC2/RKVENC2 through `/dev/mpp_service` for
  H.264/H.265 decode/encode and related MPP paths, plus the separate AV1DEC
  block via `mpp_av1dec.c` and the VSI-IOMMU provider.
- The clean-room MPP rewrite targets the same practical `/dev/mpp_service`
  surface and implements a separate VPU981/VSI AV1 backend, but has only
  source/build evidence for it.
- `ffmpeg-rockchip` registers `av1_rkmpp`, and libmpp contains AV1 parser/HAL
  code, but that userspace path needs a kernel `MPP_DEVICE_AV1DEC` backend.
- Upstream-style AV1 on RK3588 is a **different kernel path**: V4L2 stateless
  Request API through the Hantro/Verisilicon driver, backed by a dedicated
  Verisilicon IOMMU provider.

So, for this repo today:

| Use case | Expected status |
|----------|-----------------|
| `h264_rkmpp` / `hevc_rkmpp` decode and encode | Validated on the forward-port. |
| `vp9_rkmpp` decode | **Validated 2026-07-04** on board build `P1c9d`: `mpi_dec_test -t 10` decodes bit-exact (PSNR=inf) vs a software VP9 reference. |
| `av1_rkmpp` decode | **Forward port validated 2026-07-04** on board build `P1c9d` (kernel #8): AV1DEC probes, is exposed through `/dev/mpp_service`, and `mpi_dec_test -t 16777224` decodes bit-exact (PSNR=inf) vs a software AV1 reference. The clean-room rewrite backend remains hardware-unvalidated. (The measured forward-port run needs a from-source MPP; the distro `/usr/lib` lib reports `parser av1 is not registered`.) |
| upstream V4L2 stateless AV1 decode | Plausible through `../rock-5b/kernel/linux`'s Hantro + VSI-IOMMU path, but it is a different userspace API and has not been integrated into the YSP RKMPP/FFmpeg pipeline. |

## Hardware blocks and driver models

There are two separate decode blocks in play:

| Block | Vendor/RKMPP path | Upstream V4L2 path |
|-------|-------------------|--------------------|
| RKVDEC2 / VDPU381 family | The YSP forward-port and rewrite target this for H.264/H.265 and likely VP9. | Also exists upstream as media decode support, but not the `/dev/mpp_service` ABI. |
| RK3588 AV1 VPU / Verisilicon VPU981 | Rockchip BSP has a separate MPP AV1 decoder driver, `mpp_av1dec.c`; the 2026-07-03 forward-port worktree now imports it experimentally. | `drivers/media/platform/verisilicon/` binds `rockchip,rk3588-av1-vpu` and exposes `V4L2_PIX_FMT_AV1_FRAME` through stateless Request API. |

The main source of confusion is that both models talk to the same AV1 hardware
region, but they present completely different userspace contracts:

- **RKMPP/vendor model:** libmpp builds register recipes; userspace submits
  register messages to `/dev/mpp_service`; the kernel maps buffers, writes
  register classes, handles IRQ/readback, and preserves the vendor ABI.
- **V4L2 stateless model:** userspace parses AV1 bitstreams and submits per-frame
  Request API controls such as sequence/frame/tile/film-grain state; the kernel
  owns register programming through the Hantro/Verisilicon driver.

They cannot both bind the AV1 hardware at the same time.

## BSP AV1 MPP path

The Rockchip 6.1 BSP contains the missing RKMPP-side pieces:

| File/node | Role |
|-----------|------|
| `drivers/video/rockchip/mpp/mpp_av1dec.c` | MPP AV1 decoder backend, about 1,062 lines in the inspected BSP. |
| `drivers/iommu/rockchip-iommu-av1d.c` | AV1D IOMMU implementation, 795 lines. |
| `drivers/iommu/rockchip-iommu.c` | Vendor Rockchip IOMMU driver with a special `rockchip,iommu-av1d` hook. |
| `arch/arm64/boot/dts/rockchip/rk3588s.dtsi` | Vendor AV1 decoder and AV1D MMU nodes. |

The BSP AV1 decoder DT node is shaped for MPP, not Hantro:

```dts
av1d: av1d@fdc70000 {
    compatible = "rockchip,av1-decoder";
    reg = <0x0 0xfdc70000 0x0 0x800>,
          <0x0 0xfdc80000 0x0 0x400>,
          <0x0 0xfdc90000 0x0 0x400>;
    reg-names = "vcd", "cache", "afbc";
    interrupts = <GIC_SPI 108 IRQ_TYPE_LEVEL_HIGH>,
                 <GIC_SPI 107 IRQ_TYPE_LEVEL_HIGH>,
                 <GIC_SPI 106 IRQ_TYPE_LEVEL_HIGH>;
    interrupt-names = "irq_av1d", "irq_cache", "irq_afbc";
    clocks = <&cru ACLK_AV1>, <&cru PCLK_AV1>;
    clock-names = "aclk_vcodec", "hclk_vcodec";
    resets = <&cru SRST_A_AV1>, <&cru SRST_P_AV1>;
    reset-names = "video_a", "video_h";
    iommus = <&av1d_mmu>;
    rockchip,srv = <&mpp_srv>;
    rockchip,taskqueue-node = <11>;
};
```

`mpp_av1dec.c` splits userspace register messages into three classes:

| Class | Register bank | Why it matters |
|-------|---------------|----------------|
| `AV1DEC_CLASS_VCD` | `fdc70000`, `vcd` | Main decode core registers and main completion/error IRQ. |
| `AV1DEC_CLASS_CACHE` | `fdc80000`, `cache` | L2/cache status clear and cache-side controls. |
| `AV1DEC_CLASS_AFBC` | `fdc90000`, `afbc` | AFBC post-processing/input/output controls. |

The three IRQs in the vendor DT should not be overread as three fully active
software paths. The driver requests the main VCD IRQ through `mpp_dev_irq`; it
stores the AFBC IRQ number but does not install a separate AFBC handler, and the
cache IRQ is not actively handled in the inspected source. The extra IRQs look
more like a complete hardware description/future provision than active MPP logic.

## Upstream AV1 V4L2 path

The upstream-style `../rock-5b/kernel/linux` tree has a different DT shape:

```dts
av1d: video-codec@fdc70000 {
    compatible = "rockchip,rk3588-av1-vpu";
    reg = <0x0 0xfdc70000 0x0 0x800>;
    interrupts = <GIC_SPI 108 IRQ_TYPE_LEVEL_HIGH 0>;
    interrupt-names = "vdpu";
    clocks = <&cru ACLK_AV1>, <&cru PCLK_AV1>;
    clock-names = "aclk", "hclk";
    resets = <&cru SRST_A_AV1>, <&cru SRST_P_AV1>,
             <&cru SRST_A_AV1_BIU>, <&cru SRST_P_AV1_BIU>;
    iommus = <&av1d_mmu>;
};

av1d_mmu: iommu@fdca0000 {
    compatible = "rockchip,rk3588-av1-iommu", "verisilicon,iommu-1.2";
    reg = <0x0 0xfdca0000 0x0 0x600>;
    interrupts = <GIC_SPI 109 IRQ_TYPE_LEVEL_HIGH 0>;
    clocks = <&cru ACLK_AV1>, <&cru PCLK_AV1>;
    clock-names = "core", "iface";
    #iommu-cells = <0>;
};
```

That binds to:

- `drivers/media/platform/verisilicon/rockchip_vpu981_hw_av1_dec.c` for AV1
  register programming;
- `drivers/media/platform/verisilicon/rockchip_vpu_hw.c` for the RK3588 VPU981
  variant and `V4L2_PIX_FMT_AV1_FRAME` format registration;
- `drivers/iommu/vsi-iommu.c` for the dedicated Verisilicon IOMMU.

The V4L2 path uses one decode MMIO range and one decode IRQ because the kernel
driver owns the parser/control-to-register translation. It does not need to
preserve the BSP `/dev/mpp_service` register-class ABI.

## AV1 IOMMU comparison

The AV1 IOMMU is **not** the normal Rockchip IOMMU block. It has its own
register offsets and a PTA/page-table format used by the AV1/Verisilicon video
hardware. That is why the current MPP `rockchip_iommu_*` compat stubs are
insufficient.

The YSP forward-port currently provides this compile shim:

```c
static inline void rockchip_iommu_mask_irq(struct device *dev) { }
static inline void rockchip_iommu_unmask_irq(struct device *dev) { }
static inline int rockchip_iommu_enable(struct device *dev) { return -ENODEV; }
static inline int rockchip_iommu_disable(struct device *dev) { return -ENODEV; }
static inline bool rockchip_iommu_is_enabled(struct device *dev) { return false; }
static inline int rockchip_iommu_force_reset(struct device *dev) { return -ENODEV; }
```

Those stubs only avoid unresolved BSP helper symbols. They do **not** bind an
IOMMU provider, allocate page tables, program the AV1 MMU registers, handle AV1
IOMMU faults, or flush the AV1 TLB.

### Why RKVDEC2/RKVENC2 can live with the stubs

For the validated H.264/H.265 encoder and decoder blocks, the stubs are **not**
the IOMMU implementation. Normal buffer import and device-address translation
still flow through Linux's public DMA/IOMMU APIs and the upstream Rockchip IOMMU
provider:

- `dma_buf_attach()`
- `dma_buf_map_attachment_unlocked()`
- `sg_dma_address()`
- `iommu_get_domain_for_dev()`
- `iommu_attach_group()`
- `iommu_flush_iotlb_all()`

The stubbed `rockchip_iommu_*` calls are extra BSP helper hooks around fault IRQ
masking, force-reset, and `mpp_iommu_refresh()` error recovery. They are a
robustness gap, not the happy-path mapping path:

- page-fault storms may be noisier because `rockchip_iommu_mask_irq()` is a
  no-op;
- reset/error recovery may not explicitly disable/re-enable the IOMMU;
- RKVDEC2 runtime suspend/reset calls `mpp_iommu_refresh()` and ignores failure;
- RK3528/RK3562 reset helpers fall back when `rockchip_iommu_force_reset()`
  returns `-ENODEV`; this is outside the ROCK 5B target.

AV1 differs because the provider itself was missing from the validated
forward-port. Without `vsi-iommu` (or the BSP `rockchip-iommu-av1d` equivalent),
the DMA/IOMMU layer has no driver that knows how to allocate the AV1/VSI page
tables, write the PTA register, map pages, flush the AV1 TLB, or handle AV1
faults. Stubbing helper calls cannot create those IOVAs.

The upstream `vsi-iommu.c` driver is the important discovery: it is effectively
the BSP AV1D IOMMU cleaned up into a standard IOMMU provider.

| Aspect | BSP `rockchip-iommu-av1d.c` | Upstream `vsi-iommu.c` |
|--------|------------------------------|------------------------|
| Size in inspected trees | 795 lines | 791 lines |
| DT compatible | `rockchip,iommu-av1d` | `rockchip,rk3588-av1-iommu`, `verisilicon,iommu-1.2` |
| Integration model | Private `third_iommu_ops_wrap` hook inside vendor `rockchip-iommu.c` | Ordinary `struct iommu_ops`, `iommu_device_register()`, `CONFIG_VSI_IOMMU` |
| Page-table model | Two-level page tables plus PTA page | Same model |
| Key hardware actions | write PTA base, configure out-of-bound behavior, enable exceptions, enable MMU, flush TLB, report faults | Same actions |
| Maintenance posture | Vendor-private Rockchip IOMMU extension | Mainline-style standalone Verisilicon IOMMU provider |

The upstream driver is not much smaller because it still does the same real MMU
work. Its advantage is architectural: normal IOMMU API integration instead of a
private hook layer.

## Hybrid RKMPP AV1 path

The 2026-07-03 forward-port worktree uses this hybrid path:

1. Import/enable upstream-style `CONFIG_VSI_IOMMU` and `drivers/iommu/vsi-iommu.c`.
2. Add the upstream-style `av1d_mmu` node and wire the shared Hantro `av1d`
   consumer to it in `rk3588-base.dtsi`.
3. In the ROCK 5B board include, retype `&av1d` to a **vendor MPP AV1 decoder**
   node, not the Hantro node:
   `compatible = "rockchip,av1-decoder"`, three register banks, vendor clock and
   reset names, `rockchip,srv`, and `rockchip,taskqueue-node`.
4. Point that MPP node at `iommus = <&av1d_mmu>` as well.
5. Port `drivers/video/rockchip/mpp/mpp_av1dec.c` plus Kconfig/Makefile service
   registration.
6. Keep the shared RK3588 base node in Hantro form so other RK3588 boards do not
   lose the upstream V4L2 AV1 path by default.

The reason this is plausible is that `mpp_av1dec.c` itself mostly depends on the
generic MPP DMA/IOMMU layer. Its explicit IOMMU operation is
`mpp_iommu_flush_tlb()` before starting the job, and buffer import/IOVA
translation flows through generic dma-buf/IOMMU APIs. Upstream `vsi-iommu`
implements the needed provider side.

The second adversarial review pass split the remaining risk clearly:

- fixed AV1/VSI integration bugs are tracked in
  [AV1 BSP audit](./av1-bsp-audit.md);
- the no-op `rockchip_iommu_*` and Rockchip QoS helper shims remain broader
  MPP forward-port debt for the RKVENC2/RKVDEC2 error paths, not original BSP
  AV1 bugs and not the AV1/VSI provider's normal mapping path.

The risks are real:

- **DT shape mismatch:** MPP AV1 needs three register banks and vendor clock/reset
  names; the upstream Hantro AV1 node is not enough.
- **Reset recovery:** generic MPP reset calls `mpp_iommu_refresh()`, which in the
  current forward-port is backed by `rockchip_iommu_enable/disable()` stubs. A
  first successful decode may not need it, but fault/reset recovery might.
- **Fault behavior:** BSP used Rockchip helper hooks to mask IOMMU IRQs during
  fault storms. Upstream VSI reports/clears faults in a cleaner way, but MPP
  error handling may need adjustment.
- **Probe ordering and PM:** the IOMMU provider must bind/defer cleanly before
  the MPP AV1 consumer, and suspend/resume should be tested explicitly.

So this is not a guaranteed drop-in, but it is a much better starting point than
forward-porting the BSP AV1D IOMMU private hook from scratch.

## Userspace implications

Current userspace candidates:

| Userspace | Fit for RK3588 upstream AV1 V4L2 stateless |
|-----------|---------------------------------------------|
| GStreamer `v4l2codecs` / `v4l2slav1dec` | Best practical candidate. It targets stateless V4L2 codecs and can expose DMABuf-backed AV1 output. |
| Chromium | Has a V4L2 stateless decoder backend and AV1 delegate; useful for browser playback experiments. |
| upstream FFmpeg 8.1.2 | Not an answer for hardware AV1 on this board: no `av1_rkmpp`, no `av1_v4l2m2m`, and no stateless V4L2 Request AV1 frontend. |
| ffmpeg-rockchip | Has `av1_rkmpp`, but that requires the RKMPP AV1 kernel backend described above. It does not drive the upstream V4L2 stateless AV1 decoder. |
| `rockchip-vaapi` direct vendor backend | Source-inspected design: translate standard VA parsed state into VDPU jobs and submit them to this kernel's `/dev/mpp_service`, bypassing userspace libmpp while retaining `mpp_av1dec`. No direct job has been measured. |
| Bootlin `libva-v4l2-request` | Not an AV1 answer in the inspected README; MPEG2/H.264/H.265 only. |
| Bootlin `v4l2-request-test` | Not an AV1 answer in the inspected README; MPEG2/H.264 only. |

The direct vendor route is detailed in the
[`rockchip-vaapi` AV1 backend design](../../../video-libraries/vaapi/docs/av1-direct-mpp-service-backend.md).
It relies on this kernel driver only for register-class containment, DMA-BUF
fd-to-IOVA translation, scheduling, IRQ/status, and reset. Picture validation,
hardware parameter/stream construction, per-surface CDF/segmentation/MV state,
and buffer lifetime would remain userspace responsibilities.

Useful probes once a kernel exposes the upstream AV1 V4L2 node:

```bash
gst-inspect-1.0 v4l2codecs
gst-inspect-1.0 v4l2slav1dec
gst-launch-1.0 filesrc location=sample-av1.mkv ! parsebin ! v4l2slav1dec ! fakesink
```

For transcoding, the missing piece is end-to-end dmabuf plumbing. Without
`av1_rkmpp`, ffmpeg-rockchip will decode AV1 in software and then upload/import
frames into the MPP encoder; that is slower because decode is on the CPU and
because of copies. RGA only matters if the transcode also scales, crops, or
converts formats. Upstream V4L2 stateless AV1 can plausibly produce dmabufs, but
FFmpeg does not currently connect that to RKMPP encode/RGA in this stack.
