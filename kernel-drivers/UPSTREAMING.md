Cross-package ordering and coupling constraints — which items must ride the same disclosure thread, which are blocked on a sibling package's gate — live in the central [upstreaming ledger](../docs/upstreaming-ledger.md), not here. Every dated claim below (boot results, patch counts, upstream commit hashes) must be re-verified before acting on it; several rows record findings that were already stale between the date they were written and 2026-07-29.

## Rationale and evidence

### KFP-1 — Coordinated unprivileged memory-corruption disclosure
Highest-severity, best-evidenced item in the repo: all six bugs are reachable by any unprivileged member of the video group and are stated BSP-identical, with KASAN evidence ranging from use-after-free to double-free to refcount underflow. The fixes are booted and conformance-green on the production kernel (2026-07-24), so the disclosure ships a remedy alongside the report. rockchip-linux/kernel's PR channel has never merged a PR and develop-6.1 hasn't moved in seven months, so the issue carries the disclosure while the patches ride a radxa/kernel PR; Armbian's mainline rockchip64-current does not ship these drivers, so its exposure must be verified per-downstream rather than assumed.

### KFP-2 — RGA raw physical-address import crash
A complete oops trace from a single import ioctl with no job submission, reachable by anyone who can open /dev/rga. develop-5.10 and develop-6.1 both carry the same unvalidated dma_map_sg() path with no later fix, and develop-6.6 only dodges this exact crash while keeping a separately wrong DMA API call — a three-branch report behind a one-file fix. This should ride alongside or immediately after KFP-1 on the same rockchip-linux issue / radxa PR channel.
- Evidence: [rga/docs/raw-physical-import-crash.md](rga/docs/raw-physical-import-crash.md), [docs/patch-catalog.md](docs/patch-catalog.md), [tests/abi-probe.c](tests/abi-probe.c), [patches/forward-port-rk3588/README.md](patches/forward-port-rk3588/README.md)

### KFP-3 — Second-batch memory-safety
Same class and BSP-latency as KFP-1 — two more OOB writes into fixed arrays, a full-board NULL-deref lockup, and a stale IOMMU mapping reachable to freed pages — but 0053/0054 carry a documented leak-remediation trade-off a reviewer would reject as-is. 0061/0063 are PoC-validated and ready; holding the whole batch one step behind KFP-1 keeps the vendor's first impression clean at little cost.
- Evidence: [findings/2026-07-22-bsp-bug-upstream-submission-priority.md](../findings/2026-07-22-bsp-bug-upstream-submission-priority.md), [docs/patch-catalog.md](docs/patch-catalog.md), [docs/bsp-audit.md](docs/bsp-audit.md), [tests/rkvdec2-rcb-index-oob-repro.c](tests/rkvdec2-rcb-index-oob-repro.c), [tests/rkvenc2-req-fanout-oob-repro.c](tests/rkvenc2-req-fanout-oob-repro.c)
- Coupled with: KFP-1

### KFP-4 — BSP-audit HIGH remainder
Every fix here is a backport candidate by construction, but only 3 of 11 HIGH fixes have targeted hostile-path evidence, and part of the boot evidence ran against a knowingly poisoned session_attach list. The mechanical base is also a problem: 0059-0069 are shaped for the evolved tip, so the BSP-compatible form (cleanup-split/) does not currently compile and needs an 8-file divergence reconciled. Both gates are bounded, which is why this is SUBMIT-AFTER-GATE rather than HOLD.

### KFP-5 — 10-bit P010/NV15 byte-literal raster strides and UV plane offsets
The user-visible defect: the donor logic is byte-identical, so the measured P010 chroma corruption is stock vendor behavior — the corruption Jellyfin users report on vendor kernels. Evidence is booted and bit-exact, but our own patch history here is a stride-convention flip-flop (0048 regresses, 0072 repairs, 0074 covers a missed site), so the vendor must receive the composed net change, and it only holds together with the librga fork's im2d pixel-to-byte conversion. Neither rockchip-linux/kernel nor airockchip/librga merges PRs in practice, so the pair now rides two issue threads plus one radxa/kernel PR, each citing the other.
- Evidence: [docs/patch-catalog.md](docs/patch-catalog.md), [patches/forward-port-rk3588/README.md](patches/forward-port-rk3588/README.md), [findings/2026-07-24-rga3-legacy-blit-10bit-stride-convention-fault.md](../findings/2026-07-24-rga3-legacy-blit-10bit-stride-convention-fault.md), [findings/2026-07-24-rga-10bit-uv-plane-offset-still-pixel-scaled.md](../findings/2026-07-24-rga-10bit-uv-plane-offset-still-pixel-scaled.md), [findings/2026-07-25-forward-port-6-18-40-kasan-full-validation.md](../findings/2026-07-25-forward-port-6-18-40-kasan-full-validation.md), [../packaging/userspace-patches.md](../packaging/userspace-patches.md), [status.md](../status.md)
- Coupled with: RGA-1, RGA-4

### KFP-6 — RKVENC2 silently drops the terminal slice record
Both kfifo_in() call sites ignore their return value while still incrementing the write count — vendor code the forward port kept as-is — and in the field this loses the terminal marker on high-slice-count low-delay H.264, sending the MPP VEPU580 HAL into an infinite poll. The fix is small, non-fatal, compile- and checkpatch-clean, and hardware-gated, but must be presented together with the MPP HAL poll-loop hardening (MPP-1) or the kernel fix alone still leaves the userspace infinite loop.
- Evidence: [findings/2026-07-20-rkvenc2-slice-fifo-terminal-drop.md](../findings/2026-07-20-rkvenc2-slice-fifo-terminal-drop.md), [patches/forward-port-rk3588/README.md](patches/forward-port-rk3588/README.md), [docs/forward-port-status.md](docs/forward-port-status.md), [../packaging/userspace-patches.md](../packaging/userspace-patches.md), [../docs/status-ledger.md](../docs/status-ledger.md)
- Coupled with: MPP-1, MPP-2

### KFP-7 — Two unfixed vendor MPP defects (D01/D02)
D01 is reg[index] += offset with both halves user-controlled and no bound in the call chain — a repeatable, aimable arbitrary-add primitive reachable by any /dev/mpp_service opener; D02 underflows a length to ~4 GiB and hands it to copy_from_user against a small heap object. Mechanically as severe as KFP-1, but the evidence class is source-inspection only: no patch, no reproducer, no runtime evidence. D04 (stale sgt read-after-free) and D05 (unvalidated pfn_to_page on a PFNMAP VMA) are in scope for this row's second wave.
- Evidence: [docs/vendor-driver-latent-defects.md](docs/vendor-driver-latent-defects.md), [findings/2026-07-27-grd-sg-writer-source-sweep-vendor-drivers-cleared.md](../findings/2026-07-27-grd-sg-writer-source-sweep-vendor-drivers-cleared.md), [docs/patch-catalog.md](docs/patch-catalog.md), [findings/2026-07-28-dmabuf-debug-mangle-sg-table-is-the-sg-writer.md](../findings/2026-07-28-dmabuf-debug-mangle-sg-table-is-the-sg-writer.md)
- Coupled with: KFP-1

### KFP-8 — RGA2 DMA-API page-table ownership and over-4G buffer service
0049's illegal DMA-API use works by accident on the stock BSP (identity translation, no swiotlb), so on the vendor's own platform there is no victim, and 0050 is a new capability rather than a fix. Real correctness value exists — the page-table sync through a never-DMA-mapped address is a genuine DMA-API violation that DMA-debug catches the moment the platform diverges — but there is no urgency for the vendor and a nontrivial rebase cost. Holding is a scheduling judgement, not a doubt about the fix.
- Evidence: [docs/patch-catalog.md](docs/patch-catalog.md), [findings/2026-07-20-rga2-unmapped-page-table-dma-sync.md](../findings/2026-07-20-rga2-unmapped-page-table-dma-sync.md), [findings/2026-07-21-rga2-dma-api-ownership-and-over-4g-scope.md](../findings/2026-07-21-rga2-dma-api-ownership-and-over-4g-scope.md), [patches/forward-port-rk3588/README.md](patches/forward-port-rk3588/README.md), [docs/forward-port-status.md](docs/forward-port-status.md)

### KFP-9 — Defensive RGA input validation
Genuine hardening plus a diagnostics improvement (silent policy failure becomes EOPNOTSUPP with a log), but none of it is attacker-reachable memory corruption and the vendor gains no crash fix. 0045/0046 is exactly the kind of pair a busy reviewer half-applies, so the correct disposition is a later batched follow-up rather than an independent thread.
- Evidence: [docs/patch-catalog.md](docs/patch-catalog.md), [findings/2026-07-21-rga-forward-port-abi-gaps.md](../findings/2026-07-21-rga-forward-port-abi-gaps.md), [findings/2026-07-21-rga-ffmpeg-librga-conformance-root-causes.md](../findings/2026-07-21-rga-ffmpeg-librga-conformance-root-causes.md), [docs/forward-port-status.md](docs/forward-port-status.md)

### KFP-10 — The 65-patch BSP-audit MEDIUM/LOW/cleanup series
Equally latent in the BSP by the same argument that justifies the HIGH set, and already shaped for submission with real authorship. But it is the least ready artifact in the track: machine-generated, never human-merge-reviewed, never runtime-gated, and currently non-compiling. Sending 65 unverified patches to a vendor while simultaneously asking them to take memory-safety fixes seriously would be counterproductive, and rockchip-linux/kernel's zero-merge history makes a 65-patch series there a guaranteed no-op regardless.
