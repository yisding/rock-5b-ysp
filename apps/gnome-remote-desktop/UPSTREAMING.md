# Upstreaming decisions — GNOME Remote Desktop

This package holds the fork of GNOME Remote Desktop (GRD) that adds an FFmpeg/rkmpp hardware H.264 encode backend for RK3588, plus a set of upstream-reachable GRD bug fixes found along the way; this file is that package's upstream submission disposition, decided 2026-07-29. Cross-package ordering and coupling constraints — how this package's items gate or are gated by ffmpeg, Mesa, and packaging decisions elsewhere in the repo — live in the central [upstreaming ledger](../../docs/upstreaming-ledger.md), not here. Every dated claim below (states, gates, evidence dates) must be re-verified before acting on it; treat this table as a decision record, not a live status feed.

## Rationale and evidence

### GRD-1 — Handover ownership and timeout-lifetime hardening in the system daemon

Fixes GVariant ref-count misuse (a floating variant emitted while an autoptr also owns it), a leaked `GSocketConnection` from `take_client_finish`, and two timeout-cleanup bugs — a stale `abort_handover_source_id` reused by `g_clear_handle_id`, and an unconditional NULL-deref on `remote_client->socket_connection` when `TakeClient` arrives with no pending redirected connection — in `src/grd-daemon-system.c` and `src/grd-daemon-handover.c`. All three are upstream-reachable defects independent of the RKMPP backend, individually explainable, and retire real fork delta. Booted proof (two logins completing GDM-to-session handover with the encoder created on both legs, 2026-07-28) lives in the dmabuf-debug mangle-sg-table finding's section 3, not in the handover-boundary finding also cited here, which documents only the color-signaling half of that session. The MR must be rebased against upstream main, which still carries 5230bf3 (reverted only on the 50.2 stable branch this fork is based on); the local main mirror was last fetched 2026-07-21 and is stale.
- Evidence: [0010](patches/0010-daemon-system-Fix-RedirectClient-variant-ownership.patch), [0011](patches/0011-daemon-handover-Release-taken-socket-connection.patch), [0012](patches/0012-daemon-system-Harden-handover-timeout-cleanup.patch), [patches/README.md](patches/README.md), [docs/source-trees.md](../../docs/source-trees.md), [docs/status-ledger.md](../../docs/status-ledger.md), [status.md](../../status.md), [handover-boundary finding](../../findings/2026-07-28-grd-avc-fullrange-bt709-handover-boundary.md)
- Coupled with: GRD-2

### GRD-2 — Coalesce duplicate pending redirected connections instead of overwriting the pending socket

On a redirected retry using the same routing token, the old code overwrote `remote_client->socket_connection` with a fresh ref without closing or unreffing the previous connection, leaking it and re-emitting `TakeClientReady` while a `TakeClient` call was already pending. The fix adds `clear_remote_client_socket_connection()`, keeps only the newest socket, suppresses the duplicate signal while `TakeClient` is outstanding, and re-arms the abort timer. It sits exactly in the reconnection code that upstream commit 5230bf3 rewrote on main (reverted only on the 50.2 stable branch this fork tracks), so it needs its own rebase and review thread separate from GRD-1. It is also the corrected replacement for the falsified `rdp-handover-reconnect@a3a1a32` approach (GRD-16), which upstream should never see.
- Evidence: [0013](patches/0013-daemon-system-Coalesce-pending-redirected-connection.patch), [patches/README.md](patches/README.md), [docs/source-trees.md](../../docs/source-trees.md)
- Coupled with: GRD-1, GRD-15, GRD-16

### GRD-3 — AVC420 color signaling: shader emits full-range BT.709 but the encoders signal limited/unspecified

Upstream's own `grd-avc-dual-view.comp` shader implements the MS-RDPEGFX 3.3.8.3.1 conversion, which is full-range BT.709 (black maps to 0, white to 254, no studio 16-235 scaling), but the VA-API encode session sets `vui_parameters_present_flag` while zeroing `vui_fields.value`, so `video_signal_type_present_flag` and `colour_description_present_flag` stay unset and conforming clients expand the stream as limited range, muting and lifting colors. The chain was confirmed end to end on the FFmpeg backend: source inspection, ffprobe proof the two fields reach the SPS (`color_range=pc`, `color_space=bt709`), and a positive visual verdict on the Microsoft macOS RDP client after a clean reboot (2026-07-29). File as an issue carrying the spec citation and metadata evidence, with a candidate MR setting the VUI flags plus `matrix_coefficients=BT.709` in the VA-API encode session, since no VA-API-capable hardware exists here to runtime-test that variant directly. The verdict is a visual judgement on one client rather than a colorimeter measurement, which is why an issue should lead the MR.
- Evidence: [2026-07-29 fix finding](../../findings/2026-07-29-grd-fullrange-bt709-fixes-muted-colors.md), [handover-boundary finding](../../findings/2026-07-28-grd-avc-fullrange-bt709-handover-boundary.md), [fullrange-bt709.patch](../../findings/evidence/2026-07-28-grd-avc-fullrange709/fullrange-bt709.patch), [h264-metadata.txt](../../findings/evidence/2026-07-28-grd-avc-fullrange709/h264-metadata.txt), [patches/README.md](patches/README.md), [status.md](../../status.md)

### GRD-4 — Vulkan capability assumptions that silently disable all hardware encode

Two generic Vulkan robustness gaps both silently disable hardware encode: `grd_hwaccel_vulkan_get_modifiers_for_format()` queries only `VkDrmFormatModifierPropertiesList2EXT`, but Mesa's panvk advertises the extension at revision 2 while populating only the base `VkDrmFormatModifierPropertiesListEXT`, so GRD finds zero modifiers; and the AVC view creator's readback buffer demands an exact `HOST_VISIBLE|HOST_COHERENT|HOST_CACHED` memory type, which panvk never exposes, so memory-type selection fails. Both fixes are small, keep working on drivers that do populate List2 or do expose cached memory, and were the two changes that brought hardware AVC up on Mali at all, proven by live AVC420 sessions. A reviewer may argue panvk should populate List2 instead (a Mesa-side bug); offer querying List2 first with a fallback to the base list if maintainers prefer that shape.
- Evidence: [0004](patches/0004-hwaccel-vulkan-query-the-base-drm-format-modifier-li.patch), [0006](patches/0006-rdp-view-creator-avc-fall-back-when-host_cached-memo.patch), [README.md](README.md), [docs/design.md](docs/design.md)

### GRD-5 — EGL thread: read back through a driver-owned cached GPU copy instead of directly from the imported dma-buf texture

`src/grd-egl-thread.c` is shared by every GRD software/RFX path, and imported dma-buf textures can be mapped write-back-uncached on panthor/RK3588, so `glReadPixels` drives Mesa's per-pixel format-convert fallback across uncached memory, costing seconds to minutes per full-resolution frame — the Firefox/readback wedge. The fix copies into a driver-owned cached scratch texture on the GPU first, and is the root fix that let the periodic pipeline watchdog be deleted, retiring both fork delta and a whole diagnostics class. Evidence held is booted hardware plus the repo's own readback benchmark and Mesa/Panfrost transfer analysis; hardware-verified 2026-07-20/21 and shipping in the 50.2 release branch. No measurement exists here of the added copy's cost on desktop GPUs, and upstream may reasonably ask that it be conditional rather than unconditional; present the RK3588 numbers and offer to gate it. The proper Mesa-side fix (Panfrost advertising a GPU transfer mode) is a separate mesa-track MR stack that would make this unnecessary once it lands.
- Evidence: [0014](patches/0014-egl-thread-read-back-via-a-cached-GPU-copy.patch), [docs/mesa-panfrost-transfer.md](docs/mesa-panfrost-transfer.md), [docs/baseline.md](docs/baseline.md), [bench/readback_bench.c](bench/readback_bench.c), [patches/archive/pipeline-investigation/README.md](patches/archive/pipeline-investigation/README.md), [docs/source-trees.md](../../docs/source-trees.md)
- Coupled with: MESA-13, GRD-16

### GRD-6 — RDPGFX frame-acknowledgement resume can wedge a session at zero frame slots

Entirely in `src/grd-rdp-dvc-graphics-pipeline.c` and triggered by a mainstream client (Microsoft Windows App on macOS): MS-RDPEGFX queue depth `0xFFFFFFFF` suspends acknowledgements, and on resume `maybe_rewrite_frame_history()` converts the client's decoded-frame deficit back into tracked unacknowledged frames, but that reconstructed history becomes permanent if the client resumes syntactically without decode progress — a captured core showed 908 contiguous reconstructed frames, zero frame slots, live transport, and healthy hardware with no escape. The fix arms a 2 s watchdog only after a real suspend-to-resume transition that reconstructed history, keeps waiting while `totalFramesDecoded` advances, and otherwise clears stale history, unthrottles, and forces a full refresh, leaving ordinary slow-client throttling untouched. Recovery fired once live (2026-07-20) on the functionally equivalent exp6 predecessor and restored hardware submissions; the cleaned release form ships in the accepted Launchpad source but is not yet installed or focus/resume-tested, which is why filing the issue with the captured core state and protocol analysis should precede the MR.
- Evidence: [focus/resume ack wedge finding](../../findings/2026-07-20-grd-rdpgfx-focus-resume-ack-wedge.md), [0016](patches/0016-rdp-recover-stalled-frame-acknowledgements-after-res.patch), [docs/testing.md](docs/testing.md), [status.md](../../status.md), [docs/status-ledger.md](../../docs/status-ledger.md)

### GRD-7 — RFC issue: an FFmpeg-based H.264 encode-session backend for SoCs with no usable VA-API driver

An issue must precede any MR: the FFmpeg-based h264_rkmpp backend is a second hardware-acceleration framework alongside GRD's VA-API path, adds a meson feature plus roughly 1,300 lines, and allocates NV12 from `/dev/dma_heap` because panfrost's GBM cannot allocate NV12 — none of that belongs in an unsolicited large MR. The issue should state the user outcome (full-framerate RDP desktop at a few percent CPU on RK3588 instead of CPU-bound software RFX, 60 fps sustained, 1.26 ms median MPP encode), note that it fails closed and leaves VA-API preferred, and ask maintainers whether they want a generic FFmpeg encode-session sibling, an extension of the VA-API abstraction, or nothing. It should carry the color-signaling (GRD-3) and greeter device-access (GRD-14) findings as context, since both are consequences of GRD encoding on hardware GNOME has not targeted.
- Evidence: [README.md](README.md), [docs/design.md](docs/design.md), [docs/profiling.md](docs/profiling.md), [patches/README.md](patches/README.md), [status.md](../../status.md)
- Coupled with: GRD-8, GRD-14

### GRD-8 — FFmpeg/rkmpp H.264 encode-session backend

Vendor-specific by construction, so upstream appetite rather than our evidence is the real gate: the backend is proven on live RDP (macOS client, greeter and post-handover session both creating h264_rkmpp at 2064x1296, 60 fps vsync-bound, artifact-free at ~0.25 bpp), but the series carries a mainline-FFmpeg workaround (recreating the encoder after the smoke encode because rkmpp only emits SPS+PPS+IDR on the first frame, and a VBR bitrate triplet substituting for the absent QP knob), direct `/dev/dma_heap` allocation with a hand-laid-out NV12 plane layout, and a runtime dependency on an encoder fully usable only with the packaged Rockchip FFmpeg. The honest fix order is upstream FFmpeg first (the ffmpeg track owns `rkmppenc.c` and the bounded-wait branch), then GRD, and the backend is split from the recovery/backpressure work (GRD-9) to keep the first MR reviewable.
- Evidence: [0001](patches/0001-encode-session-ffmpeg-add-ffmpeg-rkmpp-h.264-encode-.patch), [0005](patches/0005-encode-session-ffmpeg-allocate-nv12-surfaces-from-th.patch), [0007](patches/0007-encode-session-ffmpeg-make-the-mainline-rkmpp-encode.patch), [README.md](README.md), [docs/profiling.md](docs/profiling.md), [docs/status-ledger.md](../../docs/status-ledger.md), [packaging/userspace-patches.md](../../packaging/userspace-patches.md)

### GRD-9 — Hardware-encode backpressure bounding, stale-view dropping, bounded cooldown and recovery

Mixed provenance: the generic half — source-serial tagging, dropping stale finished views before encode, and not queueing new view work behind a busy encode session — is arguably valid for any synchronous hardware encoder including VA-API, but the rest (measuring bitstream lock duration, entering a hardware-encode cooldown, switching to software RFX/CAPROGRESSIVE via the RDPGFX codecId mechanism, then retrying AVC on cooldown expiry) is a policy layer built around our backend's failure modes and the packaged bounded-wait FFmpeg. Verified on RK3588 with a FreeRDP test client showing AVC420 to CAPROGRESSIVE to AVC420 in one connection under a forced 300 ms lock, but submitting it before the backend has upstream buy-in is a review thread with no motivating hardware in tree. Revisit as soon as GRD-7 answers; if the answer is no backend, keep only the stale-view/busy-session parts and re-evaluate them against a VA-API reproduction.
- Evidence: [0008](patches/0008-rdp-avoid-hardware-encode-backpressure-stalls.patch), [0015](patches/0015-rdp-recover-from-stalled-hardware-encoding.patch), [MPP backpressure finding](../../findings/2026-07-19-grd-rkmpp-encoder-wedge-mpp-input-backpressure.md), [README.md](README.md), [patches/README.md](patches/README.md)
- Coupled with: GRD-8, GRD-10

### GRD-13 — Audio-quality upstream improvements: silent-negotiation warning and headless fallback-sink behavior

The one genuinely upstream-shaped idea left from the audio work: on 2026-07-20 RDP audio negotiation succeeded end to end while GRD's PipeWire registry had no Audio/Sink at all (PulseAudio held the devices), producing silence with no diagnostic, and headless remote-login sessions with no `/dev/snd` ACL or physical output have no defined fallback-sink behavior. Both are upstream-reachable and backend-independent, but nothing is implemented yet, so there is no submission unit — hold until code and one reproduction exist. The actual fix used for our board was a system PipeWire graph change, which is not upstream material.

### GRD-14 — GDM greeter cannot reach codec device nodes

Report-worthy but not a patch upstream can take as-is: the GDM greeter runs as a dynamic per-session user in only the `gdm` group, so it cannot open `/dev/dma_heap/system` or `/dev/mpp_service` (`root:video 0660`) and the encode session dies at the first `open()`; it reaches `renderD128` only because DRM nodes get a systemd `uaccess` ACL for the active seat. Tagging the codec nodes `uaccess` half-worked — logind refreshes the seat DRM node's ACL across greeter churn but leaves non-seat codec nodes pinned to whichever greeter user was first — so the grant has to go to the stable `gdm` group instead, and no existing precedent (Armbian, `uaccess`) covers a pre-login greeter encoding video. Upstream's likely answer is distro/udev policy, so raise it as context inside the GRD-7 backend RFC rather than as a standalone MR; file the systemd-facing report once from PKG-7, and keep the group ACL fork-only per PKG-6.
- Evidence: [packaging/gdm-hwenc/README.md](../../packaging/gdm-hwenc/README.md), [README.md](README.md), [docs/testing.md](docs/testing.md), [packaging/codec-udev/README.md](../../packaging/codec-udev/README.md)

### GRD-16 — Superseded experiments: single-use routing token reconnect, async-PBO and memfd readback prototypes

Falsified: the `a3a1a32` reconnect experiment treated a routing token as globally single-use and preserved displays on abort, which broke the normal two-leg GDM-to-session transition; the correct behavior is upstream's 50.2 revert (GRD-15) plus coalescing only while a socket awaits `TakeClient` (GRD-2), where consuming the socket clears pending state and leaves the token reusable for the legitimate next leg. Superseded: the async-PBO and memfd readback prototypes are raw working-tree diffs, not release commits, and the cached-GPU-copy fix (GRD-5) is the hardware-verified root fix for the same readback cliff. The two prototypes sit unlabelled on disk with no `patches/reference/README.md` to record their supersession, which is exactly the rediscovery risk this NEVER row exists to prevent.
- Evidence: [patches/README.md](patches/README.md), [docs/source-trees.md](../../docs/source-trees.md), [status.md](../../status.md)
