## Result

Mainline carries two process documents governing tool-assisted contributions.
Both are in the tree at the base this project's mainline patches target, and
neither was accounted for when those patches were prepared.

### `coding-assistants.rst` — the trailer and the DCO

Two hard rules and one format:

- **An AI agent must not add a `Signed-off-by:` tag.** Only a human can certify
  the Developer Certificate of Origin. The human submitter is responsible for
  reviewing the generated code, ensuring licence compliance, adding their own
  `Signed-off-by:`, and taking full responsibility for the contribution.
- **Attribution uses an `Assisted-by:` trailer**, in this exact shape:

  ```text
  Assisted-by: AGENT_NAME:MODEL_VERSION [TOOL1] [TOOL2]
  ```

  `AGENT_NAME` is the tool or framework, `MODEL_VERSION` the specific model, and
  the optional bracketed entries are specialised analysis tools such as
  coccinelle, sparse, smatch or clang-tidy. Basic development tools — git, gcc,
  make, editors — are explicitly not listed. The document's own example is
  `Assisted-by: Claude:claude-3-opus coccinelle sparse`.

### `generated-content.rst` — scope, disclosure, and maintainer discretion

Scope is "a meaningful amount of content in a kernel contribution was not
written by a person in the `Signed-off-by` chain, but was instead created by a
tool". Trivial tooling is out of scope: spelling and grammar fixes, identifier
completion, mechanical renaming, and reformatting.

Three parts of it bear directly on how this project works:

- **Tool-assisted *detection* counts, not just tool-assisted code.** "Detection
  of a problem and testing the fix for it is also part of the development
  process; if a tool was used to find a problem addressed by a change, that
  should be noted in the changelog." Every defect this project has sent or
  prepared for upstream was found by reading source under assistance, so this
  applies even where the final patch was typed by hand.
- **A generated changelog is itself in scope.** The document lists "the
  changelog was generated by handing the patch to a generative AI tool and
  asking it to write the changelog" as an explicit example.
- **Disclosure is expected in the cover letter and changelog**, and the document
  names what to include: which tools, the input to them (the prompts, or a
  summary of them for a longer session), which portions of the content the tool
  affected, and how the submission was tested.

Maintainers keep full discretion, listed explicitly: treat it normally, reject
it outright, demand extra testing or extra scrutiny, review it at lower
priority, or ask the submitter to demonstrate that they understand the code.
The closing rule is unambiguous: "You are expected to understand and to be able
to defend everything you submit. If you are unable to do so, then do not submit
the resulting changes." A submitter who does anyway can have the series
rejected without detailed review.

### The local trailer is a different string from the mainline one

This repository settled on `Assisted-By:` for its own commits, in an
RFC-822 name-and-address shape:

```text
Assisted-By: Claude Fable 5 <noreply@anthropic.com>
```

Mainline's trailer differs in three ways at once — the capitalisation
(`Assisted-by`), the value format (`AGENT:MODEL`, colon-separated, no display
name), and the absence of an email address:

```text
Assisted-by: Claude:claude-fable-5
```

Copying a local commit's trailer into a patch bound for a kernel mailing list
therefore produces a malformed one. The two conventions are not
interchangeable and the difference is invisible at a glance.

## Boundary

- This records what the documents require, not how any particular subsystem
  enforces them. Maintainer discretion is written into the policy itself, so
  linux-media and `iommu@lists.linux.dev` may well handle disclosed
  tool-assistance differently from each other.
- Both documents were read at one pin (`3708dd9488440`, 2026-07-30). They are
  new enough that the wording may still move; re-read them before a submission
  rather than quoting this finding.
- Nothing here establishes what a *sufficient* prompt summary looks like in
  practice. The document asks for one for longer sessions without defining the
  bar, and no example of an accepted disclosure was examined.
- The disclosure requirement is separate from patch correctness. It changes what
  a submission must say, not whether the code is right — see the
  [series self-review](2026-08-02-mainline-codec-fix-series-self-review.md) for
  the correctness half.

## Why it matters

None of the seven patches in
[`kernel-drivers/patches/mainline-codec-fixes/`](../kernel-drivers/patches/mainline-codec-fixes/README.md)
carries an `Assisted-by:` trailer; each has only `Fixes:` and
`Signed-off-by:`. The same is true of the mainline-applicable IOMMU work, which
has no extracted patches yet and so can adopt the trailer from the start.

The policy also raises the cost of the defects found in the same series. A
disclosed tool-assisted series arriving with a patch that deadlocks and two
patches that do nothing is precisely the case the "extra scrutiny or reject
outright" clause exists for, and the first such series from an unknown
contributor sets how the next one is read. The disclosure is not optional, so
the only variable this project controls is whether the code survives the
scrutiny that disclosure invites.
