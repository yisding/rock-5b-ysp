# Armbian 26.2.1 ROCK 5B raw bootloader hangs after BL31 handoff

> Scope: ROCK 5B Armbian SD/raw boot firmware path
> Source: user UART capture from Armbian 26.2.1 Minimal Debian 13 / 6.1.115,
> user report that the same image also failed with the current SPI contents and
> with zeroed SPI, downloaded image
> `Armbian_26.2.1_Rock-5b_trixie_vendor_6.1.115_minimal.img.xz`, local
> known-good Armbian bootloader packages, Armbian build source at
> `5abb97453fbabc453df560ee5b13fcc0ce31f417`, and Radxa U-Boot source at
> `6c807ac5008722e240f5282229c15a40aba4918f`
> Date: 2026-07-08
> Trust: MEASURED for the UART stop point and local baseline; HYPOTHESIS for
> the exact broken bootloader component

## The fact

The failing Armbian 26.2.1 Minimal Debian 13 / 6.1.115 boot reaches DDR init
and BL31, then stops immediately after BL31 exits to normal world:

```text
DDR 9fa84341ce typ 24/09/06-09:51:11,fwver: v1.18 ...
NOTICE: BL31: ... fwver: v1.48
WARNING: No OPTEE provided by BL2 boot loader ...
ERROR: Error initializing runtime service opteed_fast
INFO: BL31: Preparing for EL3 exit to normal world
INFO: Entry point address = 0x200000
INFO: SPSR = 0x3c9
```

The OP-TEE warning/error is not, by itself, the boot blocker. BL31 explicitly
continues to the normal-world handoff after reporting the missing BL32/OP-TEE
runtime service.

The important detail in this vendor image is that missing U-Boot output after
the BL31 handoff is not conclusive by itself. The shipped Radxa U-Boot config
has `CONFIG_DISABLE_CONSOLE=y`, so U-Boot proper can run silently. HDMI is also
not expected from the captured log alone.

On the currently working local ROCK 5B, the Armbian SPI bootloader baseline is:

```text
linux-u-boot-rock-5b-current 26.5.1
/usr/lib/linux-u-boot-current-rock-5b/rkspi_loader.img
sha256: 38b40ad14ec672899ff51118d65d10970f026f366a5c10afdbb82851b89aeacf
fwver: ddr-v1.20-b8ce94f14b,bl31-v1.48,uboot-rmbian-201-06/05/2026
```

That package also ships the raw-media boot artifacts:

```text
/usr/lib/linux-u-boot-current-rock-5b/idbloader.img  323584 bytes
/usr/lib/linux-u-boot-current-rock-5b/u-boot.itb    1461760 bytes
```

Armbian's installed platform hook writes those to block media at Rockchip's
standard offsets:

```text
idbloader.img -> sector 64
u-boot.itb    -> sector 16384
```

The user also tested the same Armbian image with both the current SPI contents
and zeroed SPI, including zeroing through this repo's utility script and Radxa's
`rsetup`, and it never booted.

Follow-up clarification: the current SPI contents do boot the existing NVMe
Armbian install successfully. The failure is therefore specific to this
Armbian 26.2.1 Minimal SD image under both raw-SD and current-SPI boot attempts,
not a general failure of the current SPI loader.

Inserted-card inspection from the working NVMe boot confirms the microSD is a
byte-for-byte write of the downloaded image where it matters:

```text
/dev/mmcblk1:   GPT PTUUID=4f831024-f98d-4ecf-9563-36ef11ab8962
/dev/mmcblk1p1: ext4 LABEL=armbi_root UUID=e0d1f6a8-8612-4976-9917-533ffb94268f
root partition sha256: 4dbef87e58b51e39d7762d737ed31a336d4ad9caf517f40424bc19e591552909
pre-rootfs 32768-sector sha256: 5de53d9f916d37552748933a7f8139be382e18344469f00d22af465afe85a8cc
```

Those hashes match the downloaded image's extracted rootfs and pre-rootfs boot
area. The SD `/boot` payload is present and structurally valid:

```text
/boot/boot.scr                         ARM Linux Script image
/boot/vmlinuz-6.1.115-vendor-rk35xx    ARM64 boot executable Image
/boot/uInitrd-6.1.115-vendor-rk35xx    AArch64 RAMDisk image
/boot/dtb/rockchip/rk3588-rock-5b.dtb  valid FDT, model "Radxa ROCK 5B"
```

So the current evidence rules out a bad card write, root UUID mismatch, missing
boot files, or an obviously malformed kernel/initrd/DTB at rest.

The downloaded image verifies correctly:

```text

Armbian_26.2.1_Rock-5b_trixie_vendor_6.1.115_minimal.img.xz
```

The rootfs pins the Armbian build source:

```text

BUILD_REPOSITORY_COMMIT=5abb97453
VERSION=26.2.1
```

The image installs `linux-u-boot-rock-5b-vendor 26.2.1`, whose metadata says:

```text
version "2017.09"
git revision "6c807ac5008722e240f5282229c15a40aba4918f"
Armbian-Original-Hash: 2017.09-S6c80-Pb178-Hd3bb-Vb338-B2eb2-R448a
UBOOT_TARGET_MAKE='BL31=.../rk3588_bl31_v1.48.elf spl/u-boot-spl.bin u-boot.dtb u-boot.itb'
```

The raw image boot gap matches the package artifacts exactly:

```text
idbloader.img -> sector 64
u-boot.itb    -> sector 16384
```

`dumpimage -l` on the shipped `u-boot.itb` shows a zero-byte FIT `fdt` image;
the later Armbian `linux-u-boot-rock-5b-vendor 26.5.1` package has the same
zero-byte component. Subsequent comparison with `linux-u-boot-rock-5b-current
26.5.1` found a valid 12,752-byte control DTB there, while Radxa's FIT generator
reads `u-boot.dtb` without declaring it as the `u-boot.itb` dependency. The
earlier "intentional" interpretation is superseded: a parallel copy/read race
is now the leading code-supported explanation, pending hardware proof. See the
[maintained comparison](../boot-firmware/docs/version-comparison.md#4-the-packaged-control-dtb-race).

The other major early-boot delta is the RK3588 DDR blob. At the image's
Armbian source commit, RK3588 uses:

```text
rk35/rk3588_ddr_lp4_2112MHz_lp5_2400MHz_v1.18.bin
```

Armbian commit `1bac6d977217039cae7193a1d6c19ae5b50c2c5f` later changed RK3588
to:

```text
rk35/rk3588_ddr_lp4_2112MHz_lp5_2400MHz_v1.20_20250926.bin
```

That matches the known-good local bootloader baseline (`ddr-v1.20`) and the
later Armbian 26.5.1 vendor package. So the raw-SD capture no longer proves a
BL33/U-Boot crash; it proves the failing zero-SPI attempt used the older 26.2.1
vendor boot chain (`ddr-v1.18`, Radxa U-Boot `6c807...`, console disabled).

There are newer Armbian 26.5.1 packages available for this board:

```text
linux-u-boot-rock-5b-current 26.5.1  -> Radxa U-Boot 39cd993e..., DDR v1.20, serial ttyS2
linux-u-boot-rock-5b-vendor  26.5.1  -> Radxa U-Boot 39cd993e..., DDR v1.20, serial ttyFIQ0
linux-image-vendor-rk35xx    26.5.1  -> kernel 6.1.115-vendor-rk35xx, git 95e85f6...
linux-dtb-vendor-rk35xx      26.5.1  -> same rk3588-rock-5b.dtb hash as 26.2.1
```

So the measured failure should be attributed to the 26.2.1 raw boot firmware
bundle as a whole, not to the two intervening Radxa source commits (which do not
touch ROCK 5B). Later artifact/build inspection identifies the empty required
control DTB and its Makefile race as the leading immediate BL33 suspect; the
DDR/SPL change remains an independent early-stage variable. The maintained
ranking and next discriminator live in the
[U-Boot comparison](../boot-firmware/docs/version-comparison.md).

The Rock 5B DTB and `boot.cmd` are byte-identical across the inspected 26.2.1
image and 26.5.1 BSP/DTB package. The kernel binary differs, and a proper test
needs the matching regenerated initrd/uInitrd because the kernel package does
not ship a ready-made `uInitrd`.

The 26.5.1 vendor kernel and DTB were later installed into the SD rootfs, the
root partition was grown to fill the card, and `update-initramfs` regenerated a
fresh U-Boot ramdisk:

```text
/boot/Image   -> vmlinuz-6.1.115-vendor-rk35xx
/boot/uInitrd -> uInitrd-6.1.115-vendor-rk35xx
/boot/dtb     -> dtb-6.1.115-vendor-rk35xx
rootdev=UUID=e0d1f6a8-8612-4976-9917-533ffb94268f
```

That still did not boot while the SD raw bootloader area was intact. Disabling
only `/boot/boot.scr` also hung and did not fall through to NVMe, which showed
the failure was not caused by the SD filesystem boot script alone.

The decisive test was to back up and zero only the SD raw loader gap, preserving
the GPT and rootfs:

```text
backup: downloads/sd-bootarea-backups/mmcblk1-raw-loader-20260709-063319.bin
sha256: 1a548204772cc3b7a68ecc2d6e917f7305e28a2ec25ddadc1a1a72b55e236311
range:  sectors 64..32767, 16744448 bytes
```

After that, the board booted from the SD successfully. Since the SD raw loader
was no longer present, that successful boot had to be using the SPI U-Boot path
to read the SD filesystem payload. The mechanism for preferring the SD raw
loader when it is present still needs a UART capture or Rockchip boot-order
source confirmation, but the practical conclusion is measured: on this setup,
a valid-but-bad raw SD loader can preempt the known-good SPI path and block both
SD and NVMe fallback.

Writing the newer Armbian 26.5.1 `linux-u-boot-rock-5b-vendor` raw artifacts to
the SD boot area changed the symptom but did not make the card boot. Unlike the
original 26.2.1 raw loader failure, HDMI did initialize, so that newer vendor
raw path appears to get at least as far as U-Boot proper or early video-capable
kernel execution. That is a different boundary from the original no-HDMI
`ddr-v1.18` capture. The remaining discriminator is to test the 26.5.1
`linux-u-boot-rock-5b-current` raw artifacts, matching the known-good SPI
loader family:

```text
/usr/lib/linux-u-boot-current-rock-5b/idbloader.img
sha256: f9dbc3b5fa6178bd68b756ac8203f05dbd78c2086d794d4d9bbbf805dcad4f72
/usr/lib/linux-u-boot-current-rock-5b/u-boot.itb
sha256: 98e2c8af220907929221c1677c4c09dc9be3bdec5fa43ded738a124763988779
```

## Why it matters / follow-up

Fast classification for future captures:

1. If this vendor image prints nothing after `SPSR = 0x3c9`, remember that
   U-Boot proper has `CONFIG_DISABLE_CONSOLE=y`; lack of U-Boot text is expected.
2. Use the first DDR line as the boot-path fingerprint. `ddr-v1.18` points to
   the failing 26.2.1 image/raw-loader path from this capture; `ddr-v1.20`
   points to later Armbian bootloader artifacts.
3. For booting this SD via known-good SPI U-Boot, leave the rootfs intact but
   remove the SD raw loader area. Back up sectors 64..32767 first, then zero
   that same range. This preserves GPT and `/boot` while forcing the board away
   from the SD raw loader path.
4. Updating the SD rootfs kernel package to 26.5.1 is not sufficient by itself:
   the SD still failed until the raw loader gap was zeroed.
5. If newer raw-loader artifacts bring up HDMI but still do not boot, classify
   that separately from the original no-HDMI 26.2.1 failure; it means the
   failing boundary moved downstream.
6. Do not use `dumpimage`'s zero-byte `fdt` entry alone as a corruption test for
   this vendor path; compare against a known-good vendor package first.
