# Armbian 26.2.1 ROCK 5B raw bootloader hangs after BL31 handoff

> Scope: ROCK 5B Armbian SD/raw boot firmware path
> Source: user UART capture from Armbian 26.2.1 Minimal Debian 13 / 6.1.115,
> user report that the same image also failed with the current SPI contents and
> with zeroed SPI, downloaded image
> `Armbian_26.2.1_Rock-5b_trixie_vendor_6.1.115_minimal.img.xz`, local
> known-good Armbian bootloader packages, Armbian build source at
> `5abb97453fbabc453df560ee5b13fcc0ce31f417`, and Radxa U-Boot source at
> `6c807ac5008722e240f5282229c15a40aba4918f`
> Date: 2026-07-08
> Trust: MEASURED for the UART stop point and local baseline; HYPOTHESIS for
> the exact broken bootloader component

## The fact

The failing Armbian 26.2.1 Minimal Debian 13 / 6.1.115 boot reaches DDR init
and BL31, then stops immediately after BL31 exits to normal world:

```text
DDR 9fa84341ce typ 24/09/06-09:51:11,fwver: v1.18 ...
NOTICE: BL31: ... fwver: v1.48
WARNING: No OPTEE provided by BL2 boot loader ...
ERROR: Error initializing runtime service opteed_fast
INFO: BL31: Preparing for EL3 exit to normal world
INFO: Entry point address = 0x200000
INFO: SPSR = 0x3c9
```

The OP-TEE warning/error is not, by itself, the boot blocker. BL31 explicitly
continues to the normal-world handoff after reporting the missing BL32/OP-TEE
runtime service.

The important detail in this vendor image is that missing U-Boot output after
the BL31 handoff is not conclusive by itself. The shipped Radxa U-Boot config
has `CONFIG_DISABLE_CONSOLE=y`, so U-Boot proper can run silently. HDMI is also
not expected from the captured log alone.

On the currently working local ROCK 5B, the Armbian SPI bootloader baseline is:

```text
linux-u-boot-rock-5b-current 26.5.1
/usr/lib/linux-u-boot-current-rock-5b/rkspi_loader.img
sha256: 38b40ad14ec672899ff51118d65d10970f026f366a5c10afdbb82851b89aeacf
fwver: ddr-v1.20-b8ce94f14b,bl31-v1.48,uboot-rmbian-201-06/05/2026
```

That package also ships the raw-media boot artifacts:

```text
/usr/lib/linux-u-boot-current-rock-5b/idbloader.img  323584 bytes
/usr/lib/linux-u-boot-current-rock-5b/u-boot.itb    1461760 bytes
```

Armbian's installed platform hook writes those to block media at Rockchip's
standard offsets:

```text
idbloader.img -> sector 64
u-boot.itb    -> sector 16384
```

The user also tested the same Armbian image with both the current SPI contents
and zeroed SPI, including zeroing through this repo's utility script and Radxa's
`rsetup`, and it never booted.

The downloaded image verifies correctly:

```text
ff6e002c5909deea13f6f5328f8bada646544c5222cb997c049dc9eb162b8e03
Armbian_26.2.1_Rock-5b_trixie_vendor_6.1.115_minimal.img.xz
```

The rootfs pins the Armbian build source:

```text
BUILD_REPOSITORY_URL=https://github.com/armbian/build
BUILD_REPOSITORY_COMMIT=5abb97453
VERSION=26.2.1
```

The image installs `linux-u-boot-rock-5b-vendor 26.2.1`, whose metadata says:

```text
version "2017.09"
git revision "6c807ac5008722e240f5282229c15a40aba4918f"
Armbian-Original-Hash: 2017.09-S6c80-Pb178-Hd3bb-Vb338-B2eb2-R448a
UBOOT_TARGET_MAKE='BL31=.../rk3588_bl31_v1.48.elf spl/u-boot-spl.bin u-boot.dtb u-boot.itb'
```

The raw image boot gap matches the package artifacts exactly:

```text
idbloader.img -> sector 64
u-boot.itb    -> sector 16384
```

`dumpimage -l` on the shipped `u-boot.itb` shows a zero-byte FIT `fdt` image.
That initially looked suspicious, but it is not the differentiator: the later
Armbian `linux-u-boot-rock-5b-vendor 26.5.1` package has the same zero-byte FIT
`fdt`. Treat it as intentional for this Radxa vendor U-Boot path, not as proof
of corruption.

The strongest source-level delta is instead the RK3588 DDR blob. At the image's
Armbian source commit, RK3588 uses:

```text
rk35/rk3588_ddr_lp4_2112MHz_lp5_2400MHz_v1.18.bin
```

Armbian commit `1bac6d977217039cae7193a1d6c19ae5b50c2c5f` later changed RK3588
to:

```text
rk35/rk3588_ddr_lp4_2112MHz_lp5_2400MHz_v1.20_20250926.bin
```

That matches the known-good local bootloader baseline (`ddr-v1.20`) and the
later Armbian 26.5.1 vendor package. So this capture no longer proves a
BL33/U-Boot crash; it proves the failing attempt used the older 26.2.1 vendor
boot chain (`ddr-v1.18`, Radxa U-Boot `6c807...`, console disabled). The
highest-confidence no-UART test is to replace only the SD raw bootloader stages
with the 26.5.1 vendor artifacts (`idbloader.img` and `u-boot.itb`) or use an
image built after the DDR v1.20 switch.

## Why it matters / follow-up

Fast classification for future captures:

1. If this vendor image prints nothing after `SPSR = 0x3c9`, remember that
   U-Boot proper has `CONFIG_DISABLE_CONSOLE=y`; lack of U-Boot text is expected.
2. Use the first DDR line as the boot-path fingerprint. `ddr-v1.18` points to
   the failing 26.2.1 image/raw-loader path from this capture; `ddr-v1.20`
   points to later Armbian bootloader artifacts.
3. For a standalone SD card, the practical experiment is to back up the card
   and write later Armbian vendor `idbloader.img` and `u-boot.itb` at sectors
   64 and 16384, respectively. That tests the image payload while replacing the
   early boot firmware.
4. Do not use `dumpimage`'s zero-byte `fdt` entry alone as a corruption test for
   this vendor path; compare against a known-good vendor package first.
